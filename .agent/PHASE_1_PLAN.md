## 1. 阶段目标

第一阶段只完成一条可以真实使用的核心路径：

```text
首次打开 App
    ↓
配置用户自己的模型 API
    ↓
选择主题与一个内置阅读技能
    ↓
生成英文文章
    ↓
生成题目、答案、解析与原文证据
    ↓
逐段翻译
    ↓
保存到本地资料库
    ↓
阅读文章并完成一次答题
```

阶段完成后，应当得到一个可在真机运行、无需自有服务端、可以通过真实模型 API 生成并完成阅读练习的 iOS App。

## 2. 为什么先做这条路径

这一阶段优先验证以下高风险问题：

- 用户自备 API Key 的配置与调用体验是否顺畅。
- 不同 OpenAI-compatible 模型的结构化输出是否足够稳定。
- 文章、题目和翻译拆分调用后，整体等待时间是否可接受。
- SwiftData 数据结构能否承载后续导入、查词和学习记录功能。
- AI 输出失败时，是否能局部重试而不丢失已经生成的内容。
- 用户是否能够完成“生成一次、阅读一次、答题一次”的基本闭环。

导入识别和点击查词都是独立复杂功能，不应在核心生成链路尚未稳定时同时展开。

## 3. 本阶段范围

### 3.1 包含

- 创建 iOS 原生项目与基础导航。
- 本地配置 OpenAI-compatible API。
- Keychain 保存和删除 API Key。
- API 连接测试。
- 一个内置 `ReadingSkill` 示例。
- 用户填写主题并选择文章长度。
- 分步生成文章、题目和段落翻译。
- 模型响应的 JSON 解码、业务校验与有限重试。
- SwiftData 保存文章、段落、题目和处理任务。
- 资料库列表。
- 基础阅读页与逐段翻译显示。
- 单项选择题作答、本地判分和解析展示。
- 展示题目的原文证据段落。
- 生成失败后的错误提示与局部重试。
- 使用 Mock Provider 的核心自动化测试。

### 3.2 不包含

- 用户导入文章或题目。
- Share Sheet。
- PDF、网页和 OCR。
- 点击单词与单词卡。
- 生词本和单词掌握状态。
- 用户阅读舒适度自适应。
- 多种考试技能和自定义技能导入。
- 判断题和简答题。
- 简答题 AI 评分。
- 流式展示正文。
- 数据导出、同步和备份。
- 完整视觉动效与高级无障碍优化。

## 4. 阶段默认决策

为避免第一阶段因产品选项过多而停滞，暂时采用以下默认值：

- 最低系统版本为 iOS 26，以直接使用 SwiftData。
- 不引入第三方依赖，优先使用 Apple 系统框架。
- 首个 Provider 使用 OpenAI-compatible Chat Completions 风格接口。
- 结构化任务优先请求 JSON Schema；供应商不支持时回退到 JSON Object 和本地校验。
- 结构化 AI 请求暂不使用流式输出，先保证完整响应和解码稳定性。
- 第一阶段只提供一个示例阅读技能；具体考试阶段可在实施前替换，不影响架构。
- 第一阶段只生成单项选择题，每篇默认 5 题。
- 翻译在生成过程中一次性完成，并按段落保存。
- 所有 AI 自动重试最多 1 次，之后由用户决定是否手动重试。
- 不配置 CloudKit，所有业务数据只存储在本地 SwiftData Store。

10. 简短的项目运行和 API 配置说明。

## 6. 工作分解

### 6.1 工作包 A：工程骨架

目标：建立可以持续开发和测试的最小工程。

任务：

- 创建 iOS App 工程，配置 SwiftUI 与 SwiftData。
- 设置最低系统版本、Bundle Identifier 和开发配置。
- 建立目录边界：`App`、`Features`、`AI`、`Models`、`Persistence`、`Security`、`Resources`、`Tests`。
- 建立根级导航结构。
- 增加统一错误类型和简单日志入口。
- 确认日志默认不输出请求头、API Key 和完整 AI 请求体。

完成标准：

- App 可以在模拟器和一台真机启动。
- 空资料库、设置页和新建入口可以正常导航。
- 测试 Target 可以运行。

### 6.2 工作包 B：领域模型与本地持久化

目标：先稳定内部结构，再接入真实模型。

任务：

- 定义 `ReadingDocument`。
- 定义 `Paragraph`。
- 定义 `Question` 与 `QuestionOption`。
- 定义 `ProcessingJob` 与 `ProcessingStage`。
- 定义来源、题型和处理状态枚举。
- 配置 SwiftData 关系和级联删除策略。
- 增加基于固定 Fixture 的保存、读取、删除测试。
- 验证 App 重启后文章、翻译和题目仍可读取。

完成标准：

- 一份固定示例阅读材料可以完整写入 SwiftData。
- 删除文档时不会残留段落、题目或处理任务。
- UI 不依赖 AI 即可展示本地 Fixture。

### 6.3 工作包 C：API 设置与密钥安全

目标：用户能够安全配置并验证自己的模型 API。

任务：

- 建立 Provider 配置模型：Base URL、模型名称和能力开关。
- 实现 `KeychainStore`。
- 使用 `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` 保存 API Key。
- 完成设置页：API Key、Base URL、模型名称。
- 增加显示/隐藏密钥、保存、替换和删除操作。
- 校验 Base URL 使用 HTTPS。
- 实现“测试连接”，区分密钥无效、模型不存在、网络失败和响应格式错误。
- 确保 API Key 不进入 SwiftData、UserDefaults 和日志。

完成标准：

- 用户可以保存配置并在重启后继续使用。
- 用户可以删除密钥，删除后无法发起生成请求。
- 测试连接可以返回清晰的成功或失败结果。

### 6.4 工作包 D：AI Provider 与结构化响应

目标：建立与具体供应商解耦的模型访问层。

任务：

- 定义 `AIProvider` 协议。
- 定义文章、题目和翻译的请求与响应 DTO。
- 实现 OpenAI-compatible Provider。
- 实现超时、取消、HTTP 状态码和供应商错误解析。
- 为结构化响应建立 `Codable` 类型。
- 实现响应清理和 JSON 解码。
- 实现业务校验器，而不只检查 JSON 是否能解码。
- 实现 Mock Provider，支持成功、超时、无效 JSON 和部分翻译缺失场景。

文章校验至少包括：

- 标题非空。
- 正文非空。
- 段落数量处于技能约束范围内。
- 每个段落拥有稳定的临时 ID。

题目校验至少包括：

- 默认生成 5 道单项选择题。
- 每道题拥有唯一 ID。
- 每道题恰好有 4 个不重复选项。
- 正确答案必须存在于选项中。
- 每道题至少引用一个有效段落 ID。

翻译校验至少包括：

- 每个英文段落都有对应译文。
- 返回结果不存在未知段落 ID。
- 译文非空。

完成标准：

- 业务层只依赖 `AIProvider`，不直接依赖供应商响应类型。
- 使用 Mock Provider 可以覆盖所有成功和失败分支。
- 无效输出不会直接写入最终文档。

### 6.5 工作包 E：阅读技能与 Prompt

目标：用一个固定技能验证可版本化的生成规则。

任务：

- 定义 `ReadingSkill` 数据结构。
- 创建一个内置 JSON 技能 Fixture。
- 实现技能资源加载和版本读取。
- 分别编写文章生成、题目生成和翻译 Prompt Builder。
- Prompt 明确要求使用稳定段落 ID。
- 题目 Prompt 要求提供正确答案、中文解析和证据段落 ID。
- 保存文档时记录 `skillID` 和 `skillVersion`。

完成标准：

- 修改技能 JSON 不需要修改 Provider 或 UI 代码。
- 生成结果能追溯到具体技能及版本。
- Prompt 单元测试验证必要约束均被写入请求。

### 6.6 工作包 F：生成处理管线

目标：串联文章、题目、翻译和本地保存，同时允许局部重试。

任务：

- 实现 `GenerationPipeline`。
- 创建草稿文档和 `ProcessingJob`。
- 按顺序执行文章生成、题目生成、段落翻译和最终校验。
- 每个成功阶段立即写入本地草稿。
- 记录当前阶段、错误类型和重试次数。
- 支持取消生成。
- 支持从失败阶段手动重试。
- 确保翻译失败不会重新生成文章和题目。
- 最终校验通过后将文档状态改为可阅读。

建议状态流：

```text
draft
  ↓
generatingArticle
  ↓
generatingQuestions
  ↓
translating
  ↓
validating
  ↓
completed
```

任一步骤可以进入 `failed(stage, error)`，重试时回到失败的步骤。

完成标准：

- 正常情况下可以从主题输入生成完整阅读材料。
- 人为制造翻译失败后，文章和题目仍然存在。
- App 重启后能够识别未完成任务并允许用户继续。
- 取消操作不会继续消耗 API 请求。

### 6.7 工作包 G：核心界面

目标：用最小但完整的界面完成一次用户旅程。

任务：

- 设置页：配置并测试 API。
- 资料库：展示处理中、失败和已完成的文档。
- 新建练习：选择技能、输入主题、选择文章长度。
- 处理页：显示当前步骤、错误和重试入口。
- 阅读页：按段落展示英文，支持单段或全文显示翻译。
- 答题页：选择答案、提交并本地判分。
- 解析页：展示正确答案、解析和证据段落。
- 无密钥、空资料库、请求中、失败和离线状态均有明确反馈。

完成标准：

- 新用户无需进入隐藏入口即可完成配置、生成、阅读和答题。
- 动态内容不会造成按钮、进度状态或正文布局跳动。
- 本地已有文章在断网时仍可正常阅读和答题。

### 6.8 工作包 H：测试与交付检查

目标：确保第一阶段成果可稳定继续迭代。

单元测试：

- Keychain 保存、读取、替换和删除。
- 技能 JSON 解码与版本读取。
- 文章、题目和翻译响应解码。
- 题目答案与选项一致性校验。
- 证据段落 ID 校验。
- 翻译完整性校验。
- Pipeline 成功路径。
- Pipeline 各阶段失败与重试。
- 文章词数边界、目标词数容差和题型计划分布校验。
- 选项数量 Schema/业务校验和响应大小门限。
- SwiftData 保存和级联删除。
- 客观题本地判分。

手工真机测试：

- 首次启动无 API 配置。
- 有效和无效 API Key。
- 慢网络、断网和请求取消。
- App 在生成中进入后台再返回。
- 生成完成后强制退出并重新打开。
- 较长英文段落与较长中文翻译的布局。
- 深色模式与动态字体基础检查。

安全检查：

- 工程中不存在硬编码 API Key。
- 日志中不存在 Authorization Header。
- SwiftData 中不存在 API Key。
- 数据删除后关联内容不再可读取。

完成标准：

- 核心逻辑测试已通过；Keychain 生命周期测试需在带 entitlement 的环境复验。
- 至少使用一个真实 OpenAI-compatible API 完成真机端到端测试（已完成）。
- 不存在阻断核心流程的已知问题；AppIcon、Archive 和 UI/无障碍属于发布前剩余事项。

## 7. 建议实施顺序

```text
里程碑 1：本地可展示
工程骨架 → 数据模型 → Fixture → 资料库与阅读页

里程碑 2：API 可调用
Keychain → 设置页 → Provider → 测试连接

里程碑 3：AI 可生成
ReadingSkill → Prompt → 文章 → 题目 → 翻译

里程碑 4：流程可恢复
ProcessingJob → 分阶段持久化 → 失败重试 → 取消

里程碑 5：闭环可交付
答题判分 → 原文证据 → 真机测试 → 安全检查
```

不建议先做完整 UI 再接入模型。里程碑 1 使用固定 Fixture 建立展示路径，里程碑 2 和 3 尽早暴露真实 API 的兼容性问题。

## 9. 阶段验收场景

使用一个全新安装的 App 执行以下场景：

1. 打开 App，资料库为空，生成入口提示需要配置 API。
2. 进入设置，填写 Base URL、模型和 API Key。
3. 测试连接成功，退出并重新打开 App，配置仍可使用。
4. 新建练习，选择内置技能，输入一个主题并开始生成。
5. App 依次显示文章、题目和翻译处理进度。
6. 生成完成后进入阅读页，文章按段落显示。
7. 用户可以逐段展开中文翻译。
8. 用户完成 5 道选择题并提交。
9. App 在本地判分，显示答案、解析和原文证据。
10. 退出并重新打开 App，文章、翻译和答题结果仍然存在。
11. 断开网络后，已有内容仍可以完整阅读。
12. 删除 API Key 后，已有内容仍可阅读，但不能生成新内容。

只有上述场景完整通过，第一阶段才算完成。

## 10. 阶段退出标准

必须满足：

- 核心验收场景全部通过。
- AI 输出异常不会产生不可打开的文档。
- 任一生成阶段失败时，不丢失此前阶段的数据。
- 用户可以明确看到当前正在消耗 API 的步骤。
- API Key 只存在于 Keychain。
- 真实设备上完成至少一次端到端生成。
- 核心逻辑有 Mock Provider 测试覆盖。

允许留到下一阶段：

- UI 视觉细节仍可优化。
- 只支持一个阅读技能。
- 只支持一种题型。
- 只验证少量 OpenAI-compatible 模型。
- 文章生成耗时尚未进行深度优化。

## 11. 第一阶段结束后的决策点

完成第一阶段后，根据真实测试结果决定第二阶段优先级：

- 如果模型结构化输出最不稳定，先强化 Provider 兼容与响应修复。
- 如果生成等待时间最影响体验，先做流式进度、并发翻译或按需翻译。
- 如果核心闭环稳定，第二阶段进入“文本导入与内容识别”。
- 如果用户最需要阅读交互，第二阶段可优先进入“点击查词与单词卡”。
- 如果不同阶段内容质量差异明显，先扩展和评估 ReadingSkill。

默认建议第二阶段优先完成文本导入和结构识别，因为它与现有统一数据模型及处理管线衔接最直接。
